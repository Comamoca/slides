** 型推論とは

型推論の簡単な概要

【改善点】
- 「入門の入門の入門」を謳うなら、ここで具体例（例: let f x = x + 1 の型が Int -> Int と推論される流れ）を1つ見せるべき。
- 聴衆は「型制約」「単一化」といった言葉を知らない前提で、まずは「既知の事実から未知を推測する」体験をさせると理解が進む。
- 「推論」の辞書的定義からの導入は良いが、型の文脈への橋渡しにやや飛躍がある。「型推論で言う『事実』とは何か」を補足するスライドがあると親切。

【改善案】
以下の内容のスライドを「事実を元に未知を推し量る」の直後に追加する：

---
=== 型推論の具体例

例として let f x = x + 1 という関数を考える。型推論が行うのは：

1. 分かっている事実（既知）
   - (+) : Int -> Int -> Int （+演算子の型）
   - 1 : Int （整数リテラルの型）
2. まだ分からないこと（未知）
   - x の型は？
   - f の型は？
3. 既知から未知を推測
   - (+) が Int を受け取るので x は Int のはず
   - (+) が Int を返すので f x 全体も Int のはず
   - よって f : Int -> Int, x : Int

👉 型推論とは「すでに型が分かっている部分」から「まだ型が分からない部分」を
   芋づる式に決定していく仕組みである。
---

この例では単純な関数を使うことで、後の「型変数」「制約生成」「単一化」の
説明の際に「さっきの f x = x + 1 の場合だと…」と参照できる伏線になる。

** HM型推論

【改善点】
- 説明が「一般的によく使われている(と思われる)」など曖昧。HMが「何を入力として何を出力するのか」を明示すると良い（例: 「抽象構文木を受け取り、型注釈なしの式に型を割り当てる」）。
- 「確定している型から制約を作り単一化で解く」という核心は書かれているが、それがどのように動作するかがこの時点ではまだ見えない。次のAlgorithm Wで具体化されると良い。

【改善案】
HM型推論を一言で表す定義を冒頭に追加する：

「HM型推論とは、型注釈のないプログラムに対し、
　型変数（仮の型）を割り当て → 式の構造から制約を生成 → 単一化で解決、
　という3段階で /最も一般的な型/ を自動的に導出するアルゴリズムである」

参考: HM型推論は1969年にJ. Roger Hindleyが初めて定式化し、1978年に
Robin Milnerが Algorithm W として再発見・実装。1982年に Luis Damas が
完全性を証明した。総称して Damas-Hindley-Milner 型システムとも呼ばれる。

** Algorithm W

【改善点】
- 「Algorithm W」と大きく掲げて期待を煽ったあと、説明が「HMの実装のひとつ」「基礎」「完全な型推論と安全かつ保守的」で終わっており、Algorithm W が /具体的に何をするのか/ が一切伝わらない。
- 最低限、以下のような自然言語での手順を示すべき:
  1. 式の各部分に型変数を割り当てる
  2. 式の構造に沿って再帰的に制約を集める
  3. 集めた制約に対して単一化を行う
  4. 単一化の結果、型変数が具体型に置き換わり式全体の型が決定される
- もしくは、簡単な疑似コードを載せると「入門」としての体裁が整う。

【改善案】
「Algorithm W」フォーカススライドの直後に、以下の手順説明スライドを追加：

---
=== Algorithm W の手順

入力: 型注釈のない式 e
出力: e の最も一般的な型

1. 型変数の割り当て
   - 式 e の各部分式にユニークな型変数 (t0, t1, t2, ...) を割り当てる
   - 例: f x = x + 1 の場合、x → t0, f → t1, 1 → t2, + → t3

2. 制約の生成
   - 式の構文木を再帰的に走査し、各部分式の使われ方から型制約を生成
   - 例: + は Int -> Int -> Int なので t0 = Int, 戻り値 = Int 等

3. 単一化（制約の解決）
   - 集めた制約を方程式として解く
   - 代入を繰り返し、すべての型変数を具体型で置き換える

4. 結果の出力
   - 単一化後の型を式全体の型として返す
   - 例: f : Int -> Int
---

備考: Algorithm W は理論上指数時間になりうるが、実用上はほぼ線形時間で
動作する。この「実用上の効率の良さ」が多くの言語で採用される理由。

** 推論の流れ

【改善点】
- 「型変数を割り当てる → 制約を割り当てる → 単一化」という3ステップは正しいが、これだけでは抽象的すぎる。
- 具体例（例: let f x = x + 1）を1つ決めて、この3ステップを /実際に適用した様子/ を見せるスライドが必須。
  - Step 1: x に型変数 t0, f に型変数 t1 を割り当て
  - Step 2: (+) の型 Int -> Int -> Int から t0 = Int, t1 = Int -> Int の制約を生成
  - Step 3: 単一化により t0 = Int, t1 = Int -> Int と決定
- スピーカーノートが空なので、発表時にどう話すか決めておく必要がある。

【改善案】
「推論の流れ」の後に、先ほどの具体例を使った /実演スライド/ を追加する：

---
=== 推論の実演: let f x = x + 1

Step 1: 型変数の割り当て
  x  → t0 （x の型はまだ不明）
  f  → t1 （f の型はまだ不明）
  1  → Int （整数リテラルなので確定）
  +  → Int -> Int -> Int （組込み演算子なので確定）

Step 2: 制約の生成
  + x 1 の部分から:
    - + の第1引数は Int なので t0 = Int
    - + の戻り値は Int なので f x 全体の戻り値型 = Int
  f x の部分から:
    - f は x を引数に取り、+ x 1 の結果を返す
    - よって t1 = t0 -> Int

Step 3: 単一化
  制約: { t0 = Int, t1 = t0 -> Int }
  t0 を Int で置き換え → t1 = Int -> Int

結果: f : Int -> Int
---

　式の構造を再帰的に辿ることで部分式から制約を積み上げ、
　単一化でそれらを一気に解決する」

** 単一化

【改善点】
- 「2つの項を等しくするプログラム」「方程式を解いている」という説明は良いが、型の文脈での具体例がない。
- 例: 「制約 t0 = Int, t1 = t0 があったとき、単一化すると t0 = Int, t1 = Int となる」という具体例を1つ見せると、「方程式を解く」の意味が聴衆に伝わる。
- 「等しい関係性の値しか解決できない」という指摘は重要。これを次の「HMと部分型」への伏線として明示的に繋げると構成が締まる。

【改善案】
「単一化」スライドの後に、以下を追加：

---
=== 単一化の具体例

以下の制約集合を例にする：

  制約1: t0 = Int
  制約2: t1 = t0
  制約3: t2 = t1 -> Int

単一化のステップ:
  1. 制約1より t0 を Int で置き換え
     → { t1 = Int, t2 = Int -> Int }
  2. t1 を Int で置き換え
     → { t2 = Int -> Int }

結果: t0 = Int, t1 = Int, t2 = Int -> Int
---

この具体例を見せた上で、口頭で次のように繋ぐ：
「単一化は『A = B』という等式しか扱えません。
　『A は B のサブタイプ（部分型）』という包含関係は扱えないのです。
　これが次の話題につながります」

** let一般化

NOTE: 時間ないのでボツにする

【改善点】

- 完成させる場合の構成案:
  1. 単一化で求めた型（例: id x = x から t0 -> t0）を示す
  2. 型変数 t0 を「任意の型」として一般化（forall a. a -> a）
  3. 「letで束縛された式に対してのみ適用される」というlet一般化の名前の由来を説明
  4. これにより id(1) も id("hello") も型が合う（多相型の恩恵）
- Elmのスライドで先にlet一般化に言及しているため、このスライドはElmより前に入れるか、Elmのスライドで簡単に補足する必要がある。

【改善案】
以下の内容でスライドを完成させる：

1. 単一化で求めた型を確認
   例: let id x = x
   単一化の結果 → id: t0 -> t0 （t0 はまだ具体化されていない型変数）

2. 型変数を「一般化」する
   残った型変数 t0 を「任意の型（∀a）」として扱う
   → id: ∀a. a -> a

3. これが「let一般化」
   - HMでは /let で束縛された変数のみ/ 多相型が許可される
   - λ（ラムダ）で束縛された変数は単相型のみ（型推論の決定可能性のため）
   - この制限により型推論が決定可能になる（Damas 1982 の証明）

4. 多相型の恩恵
   id(1)    → id: Int -> Int として使える
   id("hi") → id: String -> String として使える
   同じ id 関数が、使われる文脈ごとに異なる型として扱われる。
